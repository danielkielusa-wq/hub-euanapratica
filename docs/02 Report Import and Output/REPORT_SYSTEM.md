## Overview

The ENP Hub report system delivers personalized career diagnostic reports to leads. Reports are accessed via a secure token link, protected by email verification, and display a structured analysis following the **ROTA EUA™ methodology** (4 phases: R, O, T, A).

There are two generation pipelines:

| Pipeline | Format | Generator | Status |
|----------|--------|-----------|--------|
| **N8N** (primary) | V2 JSON | N8N automation → JS Code node | Current / Active |
| **format-lead-report** (fallback) | V1 or V2 JSON | Supabase Edge Function + LLM | Legacy / On-demand fallback |

Both pipelines write to `career_evaluations.formatted_report`. The frontend auto-detects the format and renders accordingly.

## Architecture & Data Flow

### Full Pipeline (N8N path)

```
Lead CSV Import (Admin UI)
  ↓
create-lead-user edge function
  → Creates auth user if not exists
  → Returns user_id
  ↓
career_evaluations row created
  (raw fields: name, email, area, atuacao, experiencia, etc.)
  ↓
N8N Automation triggered
  → JS Code node: scoring + phase classification
  → Prompt node: full V2 JSON report (LLM call)
  → Writes formatted_report + readiness_score + phase_id + rota_letter
  ↓
DB trigger: trigger_recommend_product_on_report
  → Fires on UPDATE of formatted_report
  → Calls recommend-product edge function via pg_net
  ↓
recommend-product edge function
  → Reads recommended_product_tier from formatted_report
  → Queries hub_services
  → LLM picks the best matching service
  → Saves: recommended_product_name, recommendation_description,
           recommendation_landing_page_url, recommendation_status='completed'
  ↓
Access token sent to lead (UUID link)
  ↓
Lead opens /report/:token
  → ReportGatekeeper: email verification
  → verify-report-access edge function validates email
  → Returns evaluation data with formatted_report
  ↓
FormattedReport component
  → isV2Report() detection
  → V2ReportContainer renders full V2 UI
  ↓
PublicReport.tsx polls recommend-product (if status ≠ 'completed')
  → CTA updates in real-time with personalized recommendation
```

### Fallback Path (format-lead-report)

Used when N8N hasn't run yet or `formatted_report` is null:

```
PublicReport.tsx detects no formatted_report
  ↓
Calls format-lead-report edge function
  → LLM generates V1 or V2 JSON
  → Stores in formatted_report
  ↓
FormattedReport renders result
```

## Report Formats: V1 vs V2

### Detection Logic

**File**: `src/types/leads.ts` — `isV2Report(data)`

```typescript
// Primary check: explicit version marker
if (report_metadata?.report_version?.startsWith('2.')) return true;

// Structural fallback (N8N reports don't include report_metadata)
if (scoring?.score_breakdown && phase_classification && barriers_analysis) return true;

return false; // → V1 rendering
```

> **Note**: N8N-generated reports pass the structural check even without `report_metadata`. This is intentional.

### V1 Format (legacy)

Generated by `format-lead-report` edge function. Sections:
`greeting`, `diagnostic`, `rota_method`, `action_plan`, `resources`, `whatsapp_keyword`, `recommendations`

Rendered by: `FormattedReport.tsx` → legacy V1 components (GreetingCard, DiagnosticGrid, RotaMethodSection, etc.)

### V2 Format (current)

Generated by N8N JS Code + LLM Prompt nodes. Sections:
`scoring`, `phase_classification`, `barriers_analysis`, `detailed_analysis`, `lead_qualification`, `timeline_milestones`, `action_plan`, `web_report_data`, `product_recommendation` *(optional — enriched post-generation)*

Rendered by: `FormattedReport.tsx` → `V2ReportContainer.tsx` → specialized V2 components.

## V2 Report Structure

### Top-Level Keys

```typescript
interface V2FormattedReportData {
  report_metadata?: {           // Optional (N8N doesn't include it)
    report_version: string;     // e.g. "2.0"
    generated_at: string;
  };
  scoring: V2Scoring;
  phase_classification: V2PhaseClassification;
  barriers_analysis: V2BarriersAnalysis;
  detailed_analysis: V2DetailedAnalysis;
  lead_qualification: V2LeadQualification;
  timeline_milestones: V2TimelineMilestone[];
  action_plan: V2ActionPlan;
  web_report_data: V2WebReportData;
  product_recommendation?: V2ProductRecommendation; // Added by enrichV2Recommendations()
}
```

### Scoring

```typescript
scoring: {
  readiness_score: number;         // 0–100
  readiness_percentual: number;    // 0–100 (same as score for display)
  max_score: number;               // 100
  score_breakdown: {
    ingles: number;                // 0–25
    experiencia_internacional: number; // 0–20
    perfil_profissional: number;   // 0–25
    preparacao: number;            // 0–15
    suporte: number;               // 0–15
  }
}
```

**Phase thresholds** (computed in N8N JS Code):

| Score | phase_id | rota_letter |
|-------|----------|-------------|
| 0–35  | 0        | Pré-R       |
| 36–60 | 1        | R-O         |
| 61–85 | 2        | O-T         |
| 86–100| 3        | T-A         |

### Phase Classification

```typescript
phase_classification: {
  phase_id: 0 | 1 | 2 | 3;
  rota_letter: string;       // "Pré-R" | "R-O" | "O-T" | "T-A"
  phase_name: string;        // e.g. "Fase de Organização"
  phase_description: string;
}
```

> **Frontend extraction**: `V2ReportContainer.extractPhaseLetter()` splits `rota_letter` by `-` and takes the last part → maps "T-A" → "A".

### ROTA Framework Progress

Part of `web_report_data.rota_framework_progress`. Rendered by `V2RotaProgress.tsx`.

```typescript
rota_framework_progress: {
  current_phase: string;    // Single letter: "R" | "O" | "T" | "A"
  phases: Array<{
    letter: string;         // "R" | "O" | "T" | "A"
    name: string;           // Full phase name
    status: string;         // "concluido" | "atual" | "futuro"
    completion_percentage: number; // 0–100
  }>
}
```

**Phase names**:
- **R**: Realidade & Direção
- **O**: Organização
- **T**: Tração
- **A**: Aceleração

> **Important**: The frontend derives `completion` from position (isPast→100, isActive→AI value, isLocked→0), not blindly from the AI-written values. Past phases always show 100% regardless of AI output.

**Deterministic N8N expressions for rota_framework_progress** (use these in the N8N prompt to avoid AI hallucination):

```json
{
  "current_phase": "{{ $json.phase_classification.rota_letter }}",
  "phases": [
    {
      "letter": "R",
      "status": "{{ $json.phase_classification.phase_id > 0 ? 'concluido' : 'atual' }}",
      "completion_percentage": "{{ $json.phase_classification.phase_id > 0 ? 100 : Math.round(($json.scoring.readiness_score / 35) * 100) }}"
    },
    {
      "letter": "O",
      "status": "{{ $json.phase_classification.phase_id > 1 ? 'concluido' : $json.phase_classification.phase_id === 1 ? 'atual' : 'futuro' }}",
      "completion_percentage": "{{ $json.phase_classification.phase_id > 1 ? 100 : $json.phase_classification.phase_id === 1 ? Math.round((($json.scoring.readiness_score - 36) / 24) * 100) : 0 }}"
    },
    {
      "letter": "T",
      "status": "{{ $json.phase_classification.phase_id > 2 ? 'concluido' : $json.phase_classification.phase_id === 2 ? 'atual' : 'futuro' }}",
      "completion_percentage": "{{ $json.phase_classification.phase_id > 2 ? 100 : $json.phase_classification.phase_id === 2 ? Math.round((($json.scoring.readiness_score - 61) / 24) * 100) : 0 }}"
    },
    {
      "letter": "A",
      "status": "{{ $json.phase_classification.phase_id === 3 ? 'atual' : 'futuro' }}",
      "completion_percentage": "{{ $json.phase_classification.phase_id === 3 ? Math.min(Math.round((($json.scoring.readiness_score - 86) / 14) * 100), 100) : 0 }}"
    }
  ]
}
```

## Product Recommendation Pipeline

### Overview

A separate async pipeline that runs after `formatted_report` is written, generating a personalized service recommendation from `hub_services`.

### Trigger Chain

```
1. formatted_report written to career_evaluations
   ↓
2. DB trigger: trigger_recommend_product_on_report (AFTER UPDATE OF formatted_report)
   → Reads supabase_edge_url + supabase_anon_key from app_configs
   → Checks for recommended_product_tier in formatted_report JSON
   → Calls recommend-product edge function via pg_net (fire-and-forget)
   ↓
3. recommend-product edge function
   → Idempotency: returns cached if status='completed'
   → Concurrency guard: skips if status='processing'
   → Reads hub_services (status IN ('available','premium') AND is_visible_in_hub=true)
   → Reads prompt from app_configs key: llm_product_recommendation_prompt
   → Calls LLM with: lead_data + tier + services JSON
   → LLM returns: recommended_service_name + recommendation_description
   → Fuzzy-matches service name to hub_services.name
   → Saves: recommended_product_name, recommendation_description,
            recommendation_landing_page_url, recommendation_status='completed'
```

### Fallback: Frontend Polling

If the DB trigger didn't fire (e.g., record existed before trigger), `PublicReport.tsx` polls on report load:

```typescript
// Fires when evaluation.recommendation_status !== 'completed' AND report has a tier
supabase.functions.invoke('recommend-product', { body: { evaluationId } })
// Retries every 3s, max 15 attempts
// Updates evaluation state when completed → CTA updates in real-time
```

### Tier → Service Mapping (LLM-driven)

The LLM receives all available services and the `recommended_product_tier`. It picks the best match. Current available services:

| Service | Type | Typical tier match |
|---------|------|--------------------|
| The Board Room: Simulação de Entrevista | consulting | T/A phase |
| Sessão Estratégica ROTA EUA – 60 min | consulting | R/O/T phase |
| Currículo e LinkedIn Internacional | consulting | O/T phase |
| Mentoria em Grupo ROTA EUA™ | live_mentoring | O/T/A phase |
| Mentoria Individual High Performance Internacional | live_mentoring | HIGH_TICKET |

### Status Values

| Status | Meaning |
|--------|---------|
| `pending` | Not yet processed |
| `processing` | LLM call in progress |
| `completed` | Recommendation saved |
| `skipped` | No tier found in report |
| `error` | LLM/parsing failure |

### Admin Prompt

Editable at `/admin/configuracoes` → Prompts IA tab.
`app_configs` key: `llm_product_recommendation_prompt`
Variables available: `{{lead_data}}`, `{{tier}}`, `{{services}}`

Required JSON response from LLM:
```json
{
  "recommended_service_name": "exact name from hub_services",
  "recommendation_description": "1-2 personalized paragraphs",
  "justification": "technical reasoning"
}
```

## Edge Functions Reference

### `verify-report-access`

**Auth**: Public (no user required)
**Purpose**: Token + email verification gate for report access

| Action | Input | Output |
|--------|-------|--------|
| `check` | `{ token }` | `{ valid: boolean }` |
| `verify` | `{ token, email }` | `{ success, evaluation }` |

Security features:
- Rate limiting: max 5 failed attempts per token per 15 min (tracked in `analytics_events`)
- Generic error messages (never reveals if token exists)
- Token expiration check (`access_token_expires_at`)
- Returns **latest evaluation by email** (ordered by `updated_at DESC`) after verification

Columns returned (PUBLIC_EVALUATION_COLUMNS):
`id, name, email, area, atuacao, experiencia, english_level, objetivo, visa_status, timeline, family_status, formatted_report, processing_status, recommendation_status, recommended_product_name, recommendation_description, recommendation_landing_page_url, formatted_at, created_at, updated_at`

---

### `recommend-product`

**Auth**: Open (anonymous allowed — evaluationId UUID is sufficient authorization)
**Purpose**: LLM-powered product recommendation, saves to `career_evaluations`

**Input**: `{ evaluationId: string }`

**Flow**:
1. Fetch evaluation record
2. Idempotency: return cached if `recommendation_status = 'completed'`
3. Concurrency guard: skip if `recommendation_status = 'processing'`
4. Mark as `processing`
5. Extract `recommended_product_tier` from `formatted_report`
6. Skip if no tier (mark as `skipped`)
7. Query `hub_services` (status IN available/premium, is_visible_in_hub=true)
8. Read prompt from `app_configs` (falls back to DEFAULT_PROMPT)
9. Call LLM (provider configured in `app_configs.llm_product_recommendation_api`)
10. Parse JSON response
11. Fuzzy-match `recommended_service_name` → `hub_services.name`
12. Save result + mark as `completed`

---

### `format-lead-report`

**Auth**: Public
**Purpose**: Legacy on-demand report generation via LLM
**Used when**: `formatted_report` is null (N8N hasn't run)

Key behavior:
- Generates V1 or V2 JSON depending on prompt configuration
- `enrichV2Recommendations()`: enriches `product_recommendation` with live hub_services data
- Caches result in `formatted_report`; respects `forceRefresh` flag

---

### `create-lead-user`

**Auth**: Admin only
**Purpose**: Creates or retrieves auth user for a lead
**Input**: `{ email, full_name, phone }`
**Output**: `{ user_id, existing: boolean }`

## Frontend Implementation

### Route: `/report/:token`

**Main file**: `src/pages/report/PublicReport.tsx`

### State Flow

```
1. Extract :token from URL
2. verify-report-access (action='check') → validate token exists
3. Show ReportGatekeeper (email input form)
4. User submits email
5. verify-report-access (action='verify') → returns evaluation + formatted_report
6. If formatted_report exists → setFormattedContent immediately (instant)
7. If processing → startPolling (format-lead-report polling, 3s backoff)
8. If null → triggerOnDemand (calls format-lead-report, fallback)
9. After content loads → recommendation polling starts (if status ≠ 'completed')
```

### Recommendation Polling

```typescript
// In PublicReport.tsx (useEffect on evaluation + formattedContent)
if (evaluation.recommendation_status === 'completed') return; // Already done

// Check for tier in report (works for V2 and N8N reports, no version gate)
const tier =
  parsed?.product_recommendation?.primary_offer?.recommended_product_tier ||
  parsed?.lead_qualification?.recommended_product_tier;
if (!tier) return; // No recommendation needed

// Poll recommend-product every 3s, up to 15 attempts
supabase.functions.invoke('recommend-product', { body: { evaluationId } })
// On 'completed': update evaluation state → V2CTAFinal re-renders with real product
```

### Component Hierarchy

```
PublicReport.tsx
└── FormattedReport.tsx  (detects V1 vs V2)
    ├── [V1] Legacy components (GreetingCard, DiagnosticGrid, ...)
    └── [V2] V2ReportContainer.tsx
        ├── ReportHeader
        ├── V2HeaderScore       — Hero + readiness score + profile chips
        ├── V2ScoreBreakdown    — Score by dimension (accordion)
        ├── V2RotaProgress      — Jornada ROTA: 4-phase timeline
        ├── V2CriticalBlockers  — Top blockers preventing progress
        ├── V2StrengthsGaps     — Strengths vs gaps (key_metrics)
        ├── V2DetailedAnalysis  — Deep dimension analysis (accordion)
        ├── V2ActionPlan        — Prioritized action steps
        ├── V2Checkpoints       — Timeline milestones
        ├── V2CTAFinal          — Product recommendation CTA (dark banner)
        └── V2ReportFooter
```

### V2CTAFinal CTA Priority

```typescript
// llmRecommendation (from recommend-product) takes priority over
// product_recommendation (from formatted_report)
const hasLlmRec = llmRecommendation?.productName;
const productName = hasLlmRec
  ? llmRecommendation.productName
  : primary?.recommended_product_name || 'Hub Gratuito'; // fallback
```

> If `recommendation_status` is not `'completed'`, `llmRecommendation` is undefined and the CTA falls back to `product_recommendation` from the report, then to "Hub Gratuito".

The `recommend-product` function queries:
```sql

```

## Security Model

| Layer | Mechanism |
|-------|-----------|
| Token validation | UUID `access_token` — hard to guess |
| Email gate | `verify-report-access` validates email matches evaluation |
| Rate limiting | Max 5 failed email attempts per token per 15 min |
| Token expiry | `access_token_expires_at` column |
| PII protection | `verify-report-access` only returns `PUBLIC_EVALUATION_COLUMNS` |
| Generic errors | Failed email check and token-not-found return same message |
| `recommend-product` | Anonymous allowed (UUID evaluationId = sufficient auth); idempotency prevents LLM cost abuse |
| RLS | `career_evaluations` has RLS; edge functions use service role key |

## Admin Configuration

### Updating the Recommendation Prompt

1. Go to `/admin/configuracoes` → **Prompts IA** tab
2. Find key `llm_product_recommendation_prompt`
3. Edit the prompt — changes take effect on next recommendation call (no deployment needed)

Available template variables:
- `{{lead_data}}` — JSON with lead profile fields
- `{{tier}}` — The `recommended_product_tier` value (e.g. `HIGH_TICKET`)
- `{{services}}` — JSON array of available hub_services

### Re-triggering Recommendations

To manually re-run for a specific lead (e.g., after updating services or prompt):

```bash
# Reset status to pending, then call the edge function
curl -X POST https://seqgnxynrcylxsdzbloa.supabase.co/functions/v1/recommend-product \
  -H "apikey: <anon_key>" \
  -H "Content-Type: application/json" \
  -d '{"evaluationId":"<uuid>"}'
```

> The idempotency guard (`status = 'completed'`) prevents re-processing. To force a re-run, reset `recommendation_status = 'pending'` in the DB first.

### Adding a New Service for Recommendations

1. Add service in `/admin/hub-services` (set `is_visible_in_hub = true`, `status = 'available'` or `'premium'`)
2. New recommendations will automatically consider the new service
3. Existing `completed` recommendations are cached — re-trigger manually if needed

## Troubleshooting

### CTA shows "Hub Gratuito" instead of real product

**Cause**: `recommendation_status` is not `'completed'` or `recommend-product` failed.

**Diagnosis**:
```sql
SELECT recommendation_status, recommended_product_name, raw_llm_response
FROM career_evaluations WHERE id = '<uuid>';
```

**Fix options**:
- If `pending`: call `recommend-product` edge function manually (see above)
- If `error`: check `raw_llm_response` for LLM error details, fix prompt or service data
- If `skipped`: report has no `recommended_product_tier` — check N8N output

### DB trigger not firing for new leads

**Check**: `supabase_edge_url` and `supabase_anon_key` exist in `app_configs`.

```sql
SELECT key, value FROM app_configs
WHERE key IN ('supabase_edge_url', 'supabase_anon_key');
```

Both must be present. If missing, run migration `20260222800000_fix_recommend_product_trigger.sql`.

### ROTA section shows wrong phase or completion

**Cause**: Old reports may have AI-written wrong values in `rota_framework_progress`.

**Fix**: Use deterministic N8N expressions (see [ROTA Framework Progress](#rota-framework-progress) section above). The frontend already derives `completion` from index position (past=100%, locked=0%), so only `current_phase` and `status` values need to be correct for the visual.
